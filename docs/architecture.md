## What this repo is

`trickfire-docs` (`TrickfireRobotics/trickfire-docs`) has two jobs that share
one codebase:

1. **A CLI framework** (`trickfire-docs init|dev|build`), published to npm and
   run via `npx` from any member repo. It scaffolds a `docs/` folder, then
   generates and runs a self-contained Fumadocs site for that repo locally.
2. **The aggregator site** - the actual `docs.trickfirerobotics.com` website.
   It syncs `docs/` content from every member repo and renders them all as one
   multi-project Fumadocs site with a project switcher.

Both are Fumadocs (Next.js + `fumadocs-mdx`) apps under the hood. The CLI's
job is to run a _single-project_ copy of essentially the same site locally;
the aggregator runs a _multi-project_ copy of it in production.

## Repo layout

```
trickfire-docs/
├── framework/          CLI source (dev|build|init) - published as the npm package
│   ├── cli.ts           entry point, dispatches to commands/
│   ├── commands/        dev.ts, build.ts, init.ts
│   ├── config/          docs.config.json schema, loading, meta.json generation
│   └── utils/           site.ts - copies/wires the `site/` template into `.trickfire-docs/`
│
├── site/                Single-project Fumadocs app template, bundled into the npm
│   │                    package and copied into every member repo's `.trickfire-docs/`
│   ├── source.config.ts  fumadocs-mdx collection config (single project, dir: "../docs")
│   └── src/lib/          source loader, icon resolution, shiki transformers, MDX components
│
├── scaffold/            Files copied into a member repo by `trickfire-docs init`
│   ├── docs.config.json  starter config
│   ├── docs/             starter markdown pages
│   └── .github/workflows/docs.yml
│
├── src/, app/            This repo's OWN Fumadocs site (the aggregator, dogfooding
│                         the same stack) - what actually serves docs.trickfirerobotics.com
├── docs/                 This repo's own docs content (what you're reading now)
├── content/              Gitignored - other repos' synced docs, populated by
│                         scripts/generate-sources.mjs / the sync workflow
├── scripts/
│   ├── generate-sources.mjs  scans content/ + docs/, writes content-sources.generated.ts
│   │                          and meta.json per project - the aggregator's equivalent
│   │                          of what framework/config/meta.ts does for a single project
│   ├── build.sh               server-side build entrypoint (git pull, install, site:build)
│   └── nginx.conf
├── source.config.ts      fumadocs-mdx config for THIS repo's own (aggregator) site
└── content-sources.generated.ts   @generated by generate-sources.mjs - do not edit
```

**Rule of thumb:** if you're changing how a _member repo's_ local docs site
looks or behaves, edit `site/`. If you're changing how the _aggregator_
(docs.trickfirerobotics.com) looks or behaves, edit `src/`/`app/` at the repo
root. If you're changing CLI behavior (`init`/`dev`/`build`, `docs.config.json`
schema, meta.json generation), edit `framework/`. The two Fumadocs apps
(`site/` and root `src/`) are separate copies, not shared - a fix to one
(styling, MDX plugins, shiki transformers) generally needs to be ported to the
other by hand.

## Components

### `framework/` - the CLI

Published as the `trickfire-docs` npm package (`bin: trickfire-docs`). Member
repos consume it via `npx trickfire-docs <command>` and never install it as a
dependency.

- **`init`** (`framework/commands/init.ts`) - copies `scaffold/docs.config.json`,
  `scaffold/docs/`, and a GitHub Actions workflow into the target repo, and
  appends `.trickfire-docs/`, `dist/`, `docs/**/meta.json` to its `.gitignore`.
- **`dev`** / **`build`** (`framework/commands/dev.ts` / `build.ts`) - both:
    1. Copy the bundled `site/` template into `<projectRoot>/.trickfire-docs/`
       (`copySiteTemplate`, always overwritten so it stays in sync with the
       installed framework version).
    2. Generate `meta.json` files from `docs.config.json`'s `sidebar` array
       (`generateMetaFiles`, `framework/config/meta.ts`) into the project's
       `docs/` directory.
    3. Symlink `.trickfire-docs/node_modules` to the framework package's own
       `node_modules` (`ensureSiteNodeModules`) - member repos never install
       Fumadocs/React/etc. themselves.
    4. Populate `.trickfire-docs/public/` from framework defaults, the project's
       `docs/assets/`, and the project's own `public/` (`ensureSitePublicDir`).
    5. Run `next dev` / `next build` with `cwd: .trickfire-docs/`. `build` then
       copies `.trickfire-docs/out/` to `<projectRoot>/dist/`.
- **`docs.config.json` schema**: `framework/config/schema.ts` (`DocsConfig`,
  `SidebarConfig`). Parsing/defaults: `framework/config/load.ts`.

### `site/` - the single-project app template

A full Fumadocs app (`source.config.ts`, `app/`, `src/`) that only knows about
one project's `docs/` folder (`dir: "../docs"`, relative to
`.trickfire-docs/`). This is what member repos actually run locally and what
gets statically exported for `trickfire-docs build`. It is copied wholesale by
`copySiteTemplate` - nothing in `.trickfire-docs/` is meant to be hand-edited
in a member repo, since it's overwritten on every `dev`/`build`.

Key files: `site/source.config.ts` (MDX/shiki config), `site/src/lib/source.ts`
(the Fumadocs loader + icon resolution), `site/src/lib/shiki-transformers.ts`
(default codeblock titles, the `$ ` shell-prompt prefix), `site/src/components/mdx.tsx`
(MDX component overrides).

### Root `src/`, `app/` - the aggregator site

This repo's own Fumadocs app, serving every project at once under
`/[repo]/[[...slug]]`. Reads from `content-sources.generated.ts`, which
`scripts/generate-sources.mjs` writes at the start of `site:dev`/`site:build`
(`postinstall` also runs it, so a fresh clone has it before the first build).

`generate-sources.mjs`:

1. Scans `content/*` (synced member repos) and this repo's own `docs/` for a
   `docs.config.json` (or, for this repo, a hardcoded `FRAMEWORK_REPO` entry).
2. Writes one `export const repo_x = defineDocs({ dir: "..." })` per project
   into `content-sources.generated.ts` - a literal file rather than a runtime
   loop, because `fumadocs-mdx` needs static `defineDocs()` calls it can
   analyze, not a dynamically-built list.
3. Writes `meta.json` into each project's content dir from its
   `docs.config.json` `sidebar` array - the same logic as
   `framework/config/meta.ts`, duplicated here because the aggregator doesn't
   go through the CLI.
4. Writes `repos.generated.json` (name/description/icon per project, used by
   the homepage project cards and switcher).

### Debian server (production)

Hosts everything at `/home/trickfire/docs/`. A self-hosted GitHub Actions
runner (label `docs`) runs directly on this machine.

```
/home/trickfire/docs/
├── content/              ← gitignored, populated by member repos' sync jobs
│   └── <repo-name>/
│       ├── docs/
│       └── docs.config.json
├── out/                  ← static export output, served by nginx
├── scripts/build.sh      ← git pull + pnpm install + site:build
└── src/, app/, node_modules/, …  ← from git
```

Two workflow types, both ending in `scripts/build.sh`:

| Workflow         | File                       | Trigger                         |
| ---------------- | -------------------------- | ------------------------------- |
| Member sync      | `sync-docs.yml` (reusable) | Called by each member repo's CI |
| Framework deploy | `deploy.yml`               | Push to `main` in this repo     |

A `cloudflared` tunnel proxies `docs.trickfirerobotics.com` to nginx on
`localhost:80` - no inbound ports opened on the server.

## Data flow: a member repo's doc update

1. Developer pushes changes to `docs/` in a member repo (on `main`).
2. That repo's `docs.yml` calls this repo's reusable `sync-docs.yml`.
3. The self-hosted runner: `rsync docs/ → content/<repo>/`, copies
   `docs.config.json`, runs `scripts/build.sh`.
4. `build.sh` → `git pull`, `pnpm install`, `pnpm site:build`.
5. `site:build` → `generate-sources.mjs` (regenerates
   `content-sources.generated.ts` + all `meta.json`) → `next build` statically
   exports the whole aggregator site to `out/`.
6. nginx serves the new `out/` immediately (static files, no server restart
   needed).

## Data flow: a member repo running `trickfire-docs dev` locally

1. Developer runs `npx trickfire-docs dev` in their repo.
2. `framework/commands/dev.ts` loads `docs.config.json`, copies `site/` into
   `.trickfire-docs/`, generates `meta.json` into `docs/`, symlinks
   `node_modules`, and runs `next dev` with `cwd: .trickfire-docs/`.
3. Fumadocs (`site/source.config.ts`, `dir: "../docs"`) picks up the project's
   `docs/*.md` + the freshly generated `meta.json` and serves a live preview
   at `localhost:3000` - a single-project version of the same site the
   aggregator will eventually render.

## What to edit for common changes

| I want to...                                                        | Edit                                                                                      |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Change `docs.config.json` fields/validation                         | `framework/config/schema.ts`, `framework/config/load.ts`                                  |
| Change how `meta.json` (sidebar structure) is generated             | `framework/config/meta.ts` **and** `scripts/generate-sources.mjs` (kept in sync by hand)  |
| Change what `trickfire-docs init` scaffolds                         | `scaffold/`, `framework/commands/init.ts`                                                 |
| Change the local dev/build pipeline (`.trickfire-docs/`)            | `framework/commands/dev.ts`, `framework/commands/build.ts`, `framework/utils/site.ts`     |
| Change styling/layout/MDX components for member repos' sites        | `site/` (and consider porting the same change to root `src/`)                             |
| Change styling/layout/MDX components for docs.trickfirerobotics.com | root `src/`, `app/` (and consider porting to `site/`)                                     |
| Change codeblock behavior (titles, shell prompt, copy button)       | `site/src/lib/shiki-transformers.ts` **and** `src/lib/shiki-transformers.ts` (duplicated) |
| Fix a bug in Fumadocs UI itself (sidebar, codeblock, etc.)          | `patches/` via `pnpm patch` - see below                                                   |
| Change the production server / nginx / systemd setup                | `scripts/build.sh`, `scripts/nginx.conf`, this doc's server section                       |
| Change what gets synced from member repos                           | `sync-docs.yml` (in `.github/`), `scripts/generate-sources.mjs`                           |

## Patching dependencies

A couple of upstream `@fumadocs/base-ui` bugs (non-collapsible sidebar folder
headers losing their classes; the codeblock copy button not respecting inline
`nd-copy-ignore` prefixes) are fixed via `pnpm patch` rather than forking the
package. The patch lives at `patches/@fumadocs__base-ui@16.13.0.patch` and is
applied automatically on `pnpm install` (see `patchedDependencies` in
`pnpm-workspace.yaml`). Because `.trickfire-docs/node_modules` is a symlink to
this repo's own `node_modules` (see `ensureSiteNodeModules`), the patch also
fixes every member repo's local site - there's nothing to do on their end.

If you hit another upstream Fumadocs bug, prefer extending this patch (or
adding a new one) over vendoring a full component copy - it's far less to
keep in sync across `site/` and root `src/`, and pnpm re-applies it on every
install.
